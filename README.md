# practice-sns

Java와 Spring Boot 학습을 위해 만든 SNS 프로젝트입니다.
RESTful API(`/api/**`)와 Thymeleaf 서버사이드 렌더링을 함께 사용합니다.

## 🛠 기술 스택

- **Java 21**, **Spring Boot 3.4.5**, Gradle
- Spring Data JPA + **MySQL**
- Spring Security + **JWT**(jjwt 0.12.5) — httpOnly 쿠키 기반 인증, 리프레시 토큰으로 자동 갱신
- **WebSocket** — DM 실시간 푸시
- Thymeleaf, Lombok
- 테스트: **JUnit 5**, Mockito, MockMvc, **H2**(인메모리)

## 📌 주요 기능

### 👤 사용자

#### 🟢 회원가입 ✅
- `id`, `password`를 전달받아 처리
- `id` 조건
  - 4~10자
  - 영어 소문자, 숫자, `.`, `_` 사용 가능
  - 숫자로만 구성될 수 없음
  - `.`, `_`가 연속되거나 맨 앞·뒤에 올 수 없음
- `password` 조건
  - 8~15자
  - 대문자, 소문자, 숫자, 특수문자 **모두** 포함
- `id` 중복 확인 후 DB에 저장
- 검증 실패 시 `GlobalExceptionHandler`가 400과 안내 문구를 반환

#### 🔐 로그인 / 로그아웃 ✅
- `id`, `password` 검증 후 액세스 토큰과 리프레시 토큰 발급
- 토큰은 **httpOnly 쿠키(`JWT_TOKEN`, `REFRESH_TOKEN`)** 로 내려가며, 이후 모든 요청에 자동으로 실려 인증에 사용됨
- 액세스 토큰이 만료돼도 리프레시 토큰이 살아 있으면 다시 로그인하지 않아도 됨 ([인증 방식](#-인증-방식) 참고)
- 로그아웃 시 쿠키를 만료시키고, 서버에 저장된 리프레시 토큰도 함께 삭제해 재발급을 차단

#### 🧑 프로필 기능 ✅
- 프로필 이미지, 닉네임 등 기본 정보 확인
- 닉네임 수정 가능 (본인 프로필에서만 수정 버튼 노출)
  - 닉네임 변경 시 JWT를 새로 발급해 쿠키를 갱신
- 프로필 하단에 해당 사용자가 작성한 게시물 피드 표시. 한 줄에 3장씩 놓이므로 12장(4줄)씩 보여주고 끝에 닿으면 이어서 불러옴
- 프로필 URL은 닉네임이 아닌 **userId** 기준 (`/profile/{userId}`)

#### 🤝 팔로우 ✅
- 프로필에서 팔로우 / 언팔로우 (토글)
- 팔로워 · 팔로잉 수 표시, 숫자를 누르면 목록 모달로 확인
  - 목록은 최근에 팔로우한 순으로 20명씩 보여주고, 목록 끝에 닿으면 다음 20명을 이어서 불러옴. 정지된 사용자는 목록에서 빠짐
- 피드 상단 **전체 / 팔로잉** 탭 — 팔로잉 탭은 내가 팔로우한 사용자의 게시물만 표시
  - 탭 전환은 페이지를 다시 불러오지 않고 무한 스크롤용 `/feed` 조각의 첫 묶음으로 피드 영역만 교체. 주소창과 뒤로 가기는 `history.pushState`로 맞춤
- 피드를 보는 사이 새 글이 올라오면 위쪽에 **새 게시물** 버튼이 뜨고, 누르면 맨 위로 올라가며 최신 묶음을 새로 받음. 누르기 전까지 보던 목록은 그대로
- 자기 자신, 정지된 사용자는 팔로우할 수 없음
- `(follower, following)` 복합 유니크 제약으로 중복 팔로우를 DB에서 차단

#### ❌ 회원탈퇴 기능 ✅
- 로그인한 사용자가 자신의 계정을 삭제
- 탈퇴 시 관련 데이터 **모두 삭제** (게시물 / 댓글 / 좋아요 / 팔로우 / 알림 / 신고)
- 탈퇴 후 쿠키 만료로 자동 로그아웃 처리

### 📝 게시물 / 💬 댓글 / ❤️ 좋아요

#### 게시물 ✅
- **제목 없이 내용과 사진**으로 작성 (인스타그램·X 스타일)
- 사진은 필수이며 `MultipartFile`로 업로드, MIME 타입 검증으로 이미지 파일만 허용
- 작성 / 조회 / 수정 / 삭제
- 수정은 작성자 본인만, 삭제는 작성자 본인 또는 관리자
- 전체 게시물 피드 조회, 피드에서 게시물 클릭 시 모달로 상세 보기
- 모달에서 작성자 닉네임 클릭 시 해당 작성자 프로필로 이동

#### 댓글 ✅
- 게시물에 댓글 추가
- 수정은 작성자 본인만, 삭제는 작성자 본인 또는 관리자
- 게시글 상세에서 원 댓글은 **최신순으로 20개씩** 보여주고, 목록 끝에 닿으면 다음 20개를 이어서 불러옴
- 답글은 접어 두고 `답글 n개 보기`를 누르면 오래된 순으로 20개씩 불러옴
- 댓글을 쓰면 모달 전체를 다시 불러오지 않고, 방금 쓴 댓글만 받아 목록에 붙임

#### 대댓글 / 멘션 ✅
- 댓글의 **답글 버튼**을 누르면 입력창에 상대 아이디가 `@아이디` 형태로 채워짐
- 답글은 **한 단만 쌓임** — 답글에 답글을 달아도 같은 원 댓글에 붙고, 누구에게 답한 것인지는 본문의 멘션이 알려줌
  - 무한 깊이 트리는 화면이 좁을수록 들여쓰기가 감당되지 않고, 렌더링에 N+1이 붙기 쉬워 채택하지 않음
- 원 댓글을 삭제하면 답글도 함께 삭제 (부모가 없는 답글은 맥락을 잃음)
- 본문의 `@아이디`는 프로필 링크로 표시되며, 존재하지 않는 아이디는 링크 없이 글자 그대로 남김
  - 해시태그와 달리 별도 테이블을 두지 않음 — "나를 멘션한 댓글 전부"처럼 거꾸로 찾는 화면이 없어 저장할 이유가 없음
  - 프로필 주소가 아이디가 아닌 id 기준이라, 서버가 `{아이디, id}` 짝을 함께 내려주어 링크를 구성

#### 좋아요 ✅
- 게시물 및 댓글에 좋아요 추가 / 취소

#### 🏷 해시태그 ✅
- 게시물 본문의 `#태그`를 정규식으로 추출해 저장 (한글 · 영문 · 숫자 · `_`)
- 대소문자를 구분하지 않으며(`#Daily` = `#daily`), 한 게시물당 최대 30개
- 본문의 해시태그는 링크로 표시되고, 누르면 해당 태그의 게시물 목록으로 이동
- 게시물 수정 시 지금 연결과 비교해 본문에서 사라진 태그만 떼고 새로 생긴 태그만 붙임
  - 예전에는 기존 연결을 전부 지우고 다시 만들어서, 태그를 그대로 두고 본문만 고쳐도 태그 수만큼 지우고 다시 넣었음. 같은 연결을 지우기 전에 다시 넣으면 유니크 제약에 걸려서 지우기를 먼저 반영하는 순서도 따로 맞춰야 했음
  - 새 태그는 태그마다 찾지 않고 이름 목록으로 한 번에 찾음(`findByNameIn`)
  - 태그 10개 기준 쿼리: 새 태그 31회 → 22회, 이미 있는 태그 21회 → 12회, 태그 그대로 본문만 수정 31회 → 1회. 남은 쿼리는 연결 저장인데, id를 DB가 정하는 방식(IDENTITY)이라 여러 행을 한 번에 넣는 배치 저장이 되지 않음

### 🔔 알림 ✅

- 팔로우 / 게시물 좋아요 / 댓글 / 멘션이 발생하면 대상 사용자에게 알림 생성
- 헤더의 종 아이콘에 읽지 않은 알림 수를 표시하고, 누르면 목록을 드롭다운으로 표시
  - 숫자는 페이지를 그릴 때 헤더에 같이 넣음. 예전에는 페이지가 뜬 뒤 알림 수, DM 수를 따로 요청해서 로그인한 사용자의 페이지 하나에 **요청 3개, 쿼리 8회**가 나갔는데 **요청 1개, 쿼리 4회**로 줄었음
  - 헤더가 있는 전체 페이지에서만 세고, 무한 스크롤 조각이나 모달 같은 부분 요청에서는 세지 않음
  - 이후 바뀌는 숫자는 WebSocket으로 받고, 연결이 끊겼다 다시 이어지면 놓친 숫자를 한 번 다시 받음(예전에는 이때 DM 수만 다시 받아 알림 수가 어긋날 수 있었음)
  - 숫자를 세고 밀어주는 일은 `BadgeService` 한 곳에서만 함. 사용자가 많아져 카운터를 Redis 같은 곳에 따로 두거나 푸시를 브로커로 보내게 되면 이 클래스 안쪽만 바꾸면 됨
  - 인증 필터는 요청마다 사용자를 DB에서 읽음. 토큰만 믿으면 이 조회를 없앨 수 있지만, 그러면 정지된 사용자가 토큰이 만료될 때까지(최대 30분) 계속 쓸 수 있어서 유지함
- 댓글 알림은 어떤 댓글인지 내용 미리보기를 함께 표시
- 알림을 누르면 해당 게시물 상세 또는 프로필로 이동
- **알림 생성 정책**
  - 본인의 행동에는 알림을 만들지 않음
  - 팔로우, 좋아요는 껐다 켜는 동작이므로 중복 알림을 만들지 않고, 취소 시 기존 알림을 삭제
  - 댓글과 멘션은 여러 번 발생할 수 있으므로 매번 새로 생성
  - 중복 제거 대상을 코드에 명시 — "댓글만 제외"로 두면 새 알림 종류가 추가될 때 아무도 정하지 않은 채 중복 제거 쪽으로 분류됨
- **멘션 알림 대상** — 본문의 `@아이디` + 답글이라면 원 댓글 작성자
  - 본문만 기준으로 삼으면, 자동으로 채워진 멘션을 지우고 답글을 남겼을 때 정작 답을 받은 사람이 알 수 없음
  - 게시글 작성자가 이미 멘션 대상이면 댓글 알림을 따로 보내지 않음
  - 정지된 계정은 인증 실패로 처리되므로 인증 이후에 알림을 생성해, 정지가 풀린 뒤에도 상태가 유지됨

### 💬 DM (1:1 채팅) ✅

- 프로필의 **메시지 버튼**으로 대화 시작, 헤더의 로켓 아이콘으로 대화 목록 진입
- 방은 두 사람 조합당 하나 — 누가 먼저 열어도 같은 방 (복합 유니크 제약)
- **전송은 REST, 수신은 WebSocket 푸시** — 상대가 접속 중이면 새 메시지를 즉시 전달
  - 핸드셰이크가 일반 HTTP 요청이라 기존 JWT 쿠키 인증을 그대로 통과
  - 소켓이 끊긴 동안은 폴링이 대신 동작하고, 3초 후 자동 재연결
- **하트비트(ping/pong)** — 서버가 30초마다 신호를 보내고 클라이언트가 응답
  - 푸시 전용이라 평소 트래픽이 0인 연결이 조용하다는 이유로 끊기는 것을 방지
  - 90초 동안 응답이 없는 세션은 죽은 연결로 보고 정리 (클라이언트도 100초 침묵 시 소켓을 직접 닫아 재연결과 폴링을 재개)
- 헤더에 **안읽음 배지** — 어느 페이지에 있든 실시간 갱신
- **읽음 표시** — 상대가 읽는 순간 내 메시지의 체크 표시가 실시간으로 켜짐
- **메시지 수정 / 삭제** — 상대가 아직 읽지 않은 내 메시지만, 우클릭 메뉴로 처리
  - 삭제는 내용을 지우고 "삭제된 메시지입니다."로 표시, 수정한 메시지는 시간 옆에 "(수정됨)" 표기
  - 메뉴가 떠 있는 사이 읽힐 수 있으므로 서버가 읽음 여부를 최종 검증
- 메시지는 최신 30개를 먼저 보여주고, "이전 메시지 보기"로 그 앞 30개씩 과거 내역 조회
  - 처음에는 페이지 번호(`OFFSET`)로 읽어서, 방을 연 뒤 메시지가 오간 만큼 밀려 **이미 보이는 메시지가 위에 다시 붙었음** (테스트로 재현: 메시지 3개가 오가면 3개 중복)
  - 피드와 같은 방식으로, 화면 맨 위 메시지의 `(createdAt, id)`보다 먼저 보낸 것부터 읽도록 바꾸고 `chat_message(room_id, created_at, id)` 인덱스를 둠
- 자기 자신, 정지된 유저와는 대화할 수 없고, 참여자가 아니면 조회와 전송 모두 불가
- 회원 탈퇴 시 참여한 방과 메시지도 함께 삭제

### 🚨 신고 ✅

- 프로필의 **더보기(`...`) 메뉴**에서 신고. 사유를 고르고 상세 내용을 남김
  - 사유: 스팸 또는 도배, 욕설 또는 괴롭힘, 음란물, 사칭, 불법 정보, 기타
  - 자기 자신은 신고할 수 없고, 아직 처리되지 않은 신고가 남아 있으면 같은 대상을 다시 신고할 수 없음
  - 처리가 끝난 뒤에는 다시 신고 가능 — 유니크 제약으로 영구히 막으면 재범을 신고할 방법이 사라짐
- **관리자 목록은 신고 한 건이 아니라 피신고자 한 명이 한 줄** (`/admin/reports`)
  - N명이 한 사람을 신고해도 N줄이 아니라 한 줄에 N으로 묶임 — 누가 많이 신고당했는지가 목록에서 바로 보임
  - 피신고자 정보까지 `JOIN`으로 함께 집계해 쿼리 한 번으로 조회
  - **대기 중 / 처리 완료** 탭으로 구분하며, 탭 상태를 쿼리에 남겨 뒤로가기와 새로고침이 그대로 동작
  - 대기 탭은 건수 순, 처리 완료 탭은 마지막 처리 시각 순 — 이력을 볼 때는 최근 조치가 위에 있어야 함
- **악성 신고자는 신고 건수가 아니라 반려 비율로 가려냄**
  - 나쁜 사용자를 잘 찾아내는 사람도 건수는 높으므로, 건수만 보면 성실한 신고자를 제재하게 됨
  - 상세 화면에서 신고자마다 **최근 30일 신고 수와 그중 반려된 수**를 함께 표시 (7일은 표본이 한두 건이라 비율이 크게 튐)
  - 신고자별 집계는 `IN` + `GROUP BY` 배치 조회 한 번으로 처리
- **처리는 피신고자 단위와 신고 한 건 단위를 함께 제공**
  - 정지를 누르면 해당 사용자를 정지시키고 대기 중인 신고를 모두 인정 처리
  - 묶어서만 처리하면 정당한 신고 여러 건에 악성 신고 한 건이 섞였을 때 그 한 건까지 인정으로 집계되어 위 비율이 흐려짐
  - 반려할 대기 신고가 없으면 전체 반려 버튼은 비활성화 (숨기면 옆 버튼들의 위치가 화면마다 달라짐)
- 상태 컬럼은 `ENUM`이 아닌 `VARCHAR` — `ddl-auto=update`는 기존 컬럼 정의를 바꾸지 않아, `ENUM`으로 굳으면 사유나 상태를 추가할 때 저장이 잘림

## ⚡ 페이징과 쿼리 최적화

- 피드(전체, 팔로잉, 해시태그)는 10개씩 `Slice`로 조회하고, 화면에서는 **무한 스크롤**로 이어서 불러옴
  - 처음에는 페이지 번호(`OFFSET`)로 읽었는데, 피드를 보는 사이 새 글이 올라오면 한 칸씩 밀려 **이미 본 글이 다음 페이지에 다시 나왔음** (테스트로 재현). 정렬도 `created_at` 하나뿐이라 시각이 같은 글은 순서가 정해지지 않았음
  - 다음 묶음을 이미 보여준 마지막 글의 `(createdAt, id)`보다 먼저 쓴 글부터 읽도록 바꿈(키셋 페이징). 새 글이 올라와도 밀리지 않고, `id`가 순서를 하나로 정함. 이 순서 그대로 `post(created_at, id)`, `post(user_id, created_at, id)` 인덱스를 둠
  - 팔로잉 피드는 팔로우 목록 전체를 자바로 가져와 `IN`에 넣던 것을 서브쿼리로 바꿔, 팔로우 수와 관계없이 쿼리 4번
  - 세 피드가 같은 조건(정지 사용자 제외)과 순서를 쓰도록 쿼리 조각을 `PostRepository` 상수 한 곳에 두고, 탭과 태그를 해석하는 규칙은 `FeedQuery` 한 곳에 둠
- 새 글 확인은 서버가 알려주는(WebSocket) 방식 대신 화면이 묻는 방식으로 함
  - 서버가 알려주면 글 하나마다 받을 사람 수만큼 보내야 하고(팔로워가 많은 사람일수록 커짐), 서버가 여러 대가 되면 중계가 필요함. "새 글이 있다"는 표시는 조금 늦어도 되는 정보라 그 비용을 치를 이유가 없음
  - 피드를 보는 동안 60초마다 "맨 위 글의 `(createdAt, id)`보다 나중 글이 있나"를 묻고, 피드가 안 보이면(`document.hidden`) 묻지 않다가 돌아오면 바로 묻음. 개수를 세지 않고 한 행만 찾으면 멈춤
  - 전체 피드의 맨 위 글은 누구에게나 같으므로 서버가 5초 동안 기억해 두고 비교만 함(`LatestFeedPost`). 접속자가 늘어도 DB 조회는 5초에 한 번이고, 새 글이 올라오면 바로 지움. 팔로잉, 해시태그 피드는 사람과 태그마다 답이 달라 인덱스로 한 행만 확인
- 초기에는 게시물마다 좋아요 수 · 좋아요 여부 · 댓글 수를 각각 조회해 **게시물 18건에 쿼리가 59번** 나갔음
- 게시물 id를 모아 종류별로 한 번씩만 조회하도록 바꾸고(`GROUP BY` 집계 + `IN` 조회), 작성자는 `JOIN FETCH`로 함께 조회하여 **쿼리 6번**으로 감소
- 정지 사용자 필터링도 자바 코드가 아닌 쿼리 조건으로 옮겨, 페이징 개수가 어긋나지 않도록 수정
- 게시글 상세의 댓글도 같은 구조였음 — 댓글마다 좋아요 수와 좋아요 여부를 각각 조회하던 것을 배치 조회로 전환. 대댓글이 생기며 댓글 수가 늘어나 방치하면 그만큼 커지는 부분이었음
- 멘션도 댓글마다 조회하지 않고, 한 게시글의 모든 `@아이디`를 모아 한 번에 조회
- 댓글 작성자는 `post.getComments()`로 읽은 뒤 댓글마다 따로 조회되고 있었음. 댓글을 작성자와 함께 `JOIN FETCH`로 가져오도록 바꿔 **작성자 20명 기준 쿼리 27번 → 6번**, 작성자 수와 관계없이 일정. 댓글 순서도 `createdAt, id`로 고정
- 쿼리 수를 고정한 뒤에도 게시글 상세는 댓글을 **전부** 읽어 그렸음. 댓글이 많은 게시글일수록 읽는 행, `IN` 목록, 응답 크기가 그대로 커지고, 댓글을 하나 달 때마다 이 전체를 다시 불러왔음
  - 원 댓글을 20개씩 끊어 읽도록 바꿈. 다음 묶음은 페이지 번호(`OFFSET`)가 아니라 이미 보여준 마지막 댓글의 `(createdAt, id)` 다음부터 읽음 — 앞에 새 댓글이 생겨도 밀리거나 겹치지 않고, 뒤로 갈수록 건너뛸 행이 늘어나지 않음
  - 이 순서 그대로 `comment(post_id, parent_id, created_at, id)`, `comment(parent_id, created_at, id)` 인덱스를 둠
  - 작성자는 계속 `JOIN FETCH`로 함께 읽음. 댓글 하나에 작성자는 한 명이라 join해도 행이 늘지 않아, `LIMIT`이 DB에서 그대로 걸림
  - 같은 조건(H2, MockMvc로 모달 요청 100회 중앙값)에서 **댓글 1,000개 게시글의 모달 응답 45ms → 4ms, 응답 크기 1.9MB → 38KB**. 이제 응답 크기는 댓글 수와 관계없이 일정
- 팔로워/팔로잉 목록도 같은 문제가 있었음 — 팔로우 관계를 전부 읽은 뒤 사람마다 따로 조회해 **팔로워 100명이면 쿼리 102번**, 정지 사용자는 자바에서 걸러냄
  - 화면에 필요한 칸(id, 아이디, 프로필 사진)만 DTO로 바로 꺼내도록 바꿔, 팔로워 수와 관계없이 **쿼리 2번**(사용자 존재 확인 + 목록). 엔티티로 할 일이 없는 목록이라 fetch join 대신 프로젝션을 씀
  - 정지 사용자 조건을 쿼리로 옮김. 20명씩 끊어 읽으면서 자바에서 거르면 한 묶음이 20명보다 적게 나가기 때문
  - 댓글과 같은 방식으로 `(followedAt, id)` 기준 키셋 페이징과 `follow(following_id, followed_at, id)`, `follow(follower_id, followed_at, id)` 인덱스
- 배지 숫자(안 읽은 알림, 안 읽은 DM)는 로그인한 사용자가 페이지를 열 때마다 조회되는, 가장 자주 실행되는 쿼리라 인덱스를 둠
  - 안 읽은 알림 수는 받는 사람의 알림을 전부 열어 `is_read`를 확인하고 있었음 → `notification(recipient_id, is_read)`로 안 읽은 것만 인덱스 안에서 셈
  - 최근 알림 20개는 받는 사람의 알림 전체를 정렬하고 있었음 → `notification(recipient_id, created_at)`로 최신순 앞에서 20개만 읽음
  - 안 읽은 DM 수는 내 방들의 메시지를 전부 열어 보고 있었음 → `chat_message(room_id, is_read, sender_id)`로 인덱스만 보고 셈. `user1 OR user2` 조건은 MySQL이 두 인덱스를 합쳐(index merge) 처리하고 있어서, 서브쿼리로 바꿔도 실행 계획과 시간이 같아 쿼리는 그대로 둠
  - 실시간 푸시는 보낼 내용을 값이 아니라 만드는 방법(`Supplier`)으로 받아, 받을 사람이 접속해 있을 때만 배지 숫자를 셈. 값으로 받으면 접속 여부를 확인하기 전에 이미 계산돼 좋아요 하나, DM 하나마다 아무도 받지 않을 숫자를 세고 있었음
- **MySQL 실측** (실서비스 DB와 별개의 MySQL 9.0.1 서버, 게시글 30만, 알림 40만, 메시지 60만, `EXPLAIN ANALYZE` 7회 중앙값)

  | 쿼리 | 이전 | 이후 | 실행 계획 변화 |
  |---|---|---|---|
  | 전체 피드 첫 묶음 | 284ms | 0.07ms | 30만 행 전체 훑기 + 정렬 → 인덱스 역순으로 앞 11행 |
  | 팔로잉 피드 첫 묶음 | 147ms | 6.5ms | 임시 테이블 + 정렬 → 인덱스 역순 + 팔로우 확인 |
  | 안 읽은 알림 수 | 36.9ms | 0.02ms | 그 사람 알림 3만 행 확인 → 인덱스에서 5행만 |
  | 최근 알림 20개 | 53.2ms | 0.21ms | 3만 행 정렬 → 인덱스 역순으로 20행 |
  | 안 읽은 DM 수 | 83.7ms | 1.05ms | 내 방 메시지 전부 확인 → 인덱스에서 안 읽은 것만 |

  - 운영 DB는 `ddl-auto=update`라서, 이미 있는 테이블에도 앱을 켤 때 새 인덱스가 추가되는 것을 같은 서버에서 확인함
- "목록 끝에 닿으면 다음 묶음 부르기"는 피드, 댓글, 팔로워 목록이 같이 쓰므로 `infiniteScroll.js` 한 곳에 둠. 다음 묶음이 있는지와 불러오는 중인지는 각 화면이 판단하고, 공용 함수는 끝에 닿았는지만 알려줌
- 프로필은 그 사람의 글을 전부 읽어 그리고 있었음 → 피드와 같은 키셋 방식으로 12장씩 읽고, 게시물 수는 목록 길이 대신 `COUNT`로 셈. 글 1,000개인 사람의 프로필 응답 40ms → 6.5ms, 크기 1.36MB → 38KB (H2, MockMvc 50회 중앙값). 쿼리는 게시물 수 `COUNT`가 생겨 6회 → 7회
  - 팔로워, 팔로잉 수와 팔로우 여부는 사람을 엔티티로 읽지 않고 id로 바로 셈
- 게시글 카드 한 장은 `postCards.html`의 `card` 조각 한 곳에 두고 피드와 프로필이 같이 씀. 프로필에 카드 마크업이 복사돼 있어서 피드에만 고친 것(다음 묶음 기준값)이 생겼던 것을 정리함. 카드를 `/feed` 조각으로 받아 붙이고 첫 묶음으로 갈아 끼우는 일도 `feedList.js` 한 곳에 둠

## 🧯 실패 응답

- 서비스는 상황에 맞는 예외를 던지고, `GlobalExceptionHandler`가 그것을 응답 코드로 옮김
  - `NotFoundException` → **404** (대상이 없음)
  - `ForbiddenException` → **403** (로그인은 했지만 그 대상에는 할 수 없는 일)
  - `IllegalArgumentException` → **400** (값이 규칙에 안 맞거나, 지금 상태에서는 할 수 없는 일)
- 응답 본문은 전부 `{"message": "..."}` 한 가지 모양
- 게시글, 댓글, DM 본문은 `TextContent` 한 곳에서 검사함. 비어 있으면 안 되고, 앞뒤 공백을 뺀 값을 저장하며, 엔티티가 정한 한도(게시글 2200 / 댓글 255 / DM 1000자)를 넘으면 DB까지 가지 않고 400. 화면 입력칸의 `maxlength`도 같은 상수를 씀
- 컨트롤러에는 `try-catch`를 두지 않음. 예전에는 컨트롤러마다 같은 catch를 반복하면서 같은 상황이 화면마다 다른 코드로 나갔고, catch를 빠뜨린 경로는 500이 나갔음
- 화면을 그리는 `ViewController`는 JSON을 줄 수 없어 이 핸들러의 대상에서 빼고, 목록이나 로그인으로 되돌림

## 🔑 인증 방식

- 로그인 성공 시 서버가 **액세스 토큰(JWT, 30분)** 과 **리프레시 토큰(14일)** 을 발급해 각각 **httpOnly 쿠키**로 설정
- 인증 판정은 `JwtAuthFilter` 한 곳에서만 수행 — 컨트롤러는 `@AuthenticationPrincipal`로 결과만 받아 사용
- 클라이언트(브라우저)는 토큰을 직접 보관하지 않으며, 로그인이 필요한 페이지(예: 게시글 작성)는 서버에서 접근을 제어
- 인가 판정도 `SecurityConfig` 한 곳에 선언 — 관리자 전용 경로(`/admin/**`, `/api/reports/**` 등)를 컨트롤러가 아닌 설정에서 관리
- 인증 실패는 `AuthenticationEntryPoint`에서 **비로그인(401)** 과 **계정 정지(403)** 로 구분해 응답하고, 응답 형태는 API면 JSON, 페이지면 리다이렉트로 갈림

#### 액세스 토큰 자동 갱신 ✅

- 액세스 토큰이 만료돼도 리프레시 토큰이 유효하면 **`JwtAuthFilter`가 새 액세스 토큰을 발급하고 요청을 그대로 진행**
  - 별도의 갱신 엔드포인트를 두지 않은 이유는 Thymeleaf 서버사이드 렌더링 때문 — 페이지는 서버가 HTML을 만드는 시점에 로그인 여부가 확정되므로, 브라우저가 401을 받고 재시도하는 방식으로는 "오랜만에 접속해도 로그인 유지"를 만들 수 없음
- 리프레시 토큰은 JWT가 아닌 **난수 문자열**이며, DB에는 **SHA-256 해시**로만 저장 (취소 가능해야 하므로 자기 자신만으로 유효한 JWT를 쓰지 않음)
- **회전(rotation)** — 갱신할 때마다 리프레시 토큰도 새로 발급하고 이전 것은 교체 표시
  - 한 페이지에서 요청이 동시에 나가면 모두 같은 토큰으로 갱신을 시도하므로, 교체 직후 **60초간은 이전 토큰도 인증만 허용**해 정상 사용자가 로그아웃되지 않도록 처리
  - 회전 판정은 `UPDATE ... WHERE replaced_at IS NULL`로 DB에 위임 — 동시 요청이 각자 새 토큰을 만들어 쓰이지 않는 토큰이 쌓이는 것을 방지
  - 만료 시각은 최초 로그인 기준을 유지해 갱신으로 수명이 무한히 늘어나지 않도록 함
- **로그인 단위 관리** — 로그인 한 번을 하나의 묶음(`familyId`)으로 보고, 로그아웃 시 회전으로 파생된 토큰까지 함께 삭제. 다른 기기의 로그인은 유지
- 정지 계정은 리프레시 토큰으로도 인증되지 않으며, 인증에 실패한 경우 토큰을 회전시키지 않아 정지 해제 후 로그인 상태가 유지됨

## ▶️ 실행 방법

1. MySQL에 데이터베이스 생성
   ```sql
   CREATE DATABASE sns_db CHARACTER SET utf8mb4;
   ```

2. 프로젝트 루트의 `secrets.properties.example` 을 `secrets.properties` 로 복사하고 값 채우기 (git에 포함되지 않음)
   ```properties
   DB_USERNAME=<DB 사용자명>
   DB_PASSWORD=<DB 비밀번호>
   # HS256 서명용 랜덤 키, 32바이트 이상. 생성 예: openssl rand -base64 48
   JWT_SECRET=<시크릿 키>
   ```
   나머지 설정은 `src/main/resources/application.properties` 에 있으며, 시크릿 자리만 `${...}` 로 비워져 있다.
   배포 환경에서는 파일 대신 같은 이름의 환경변수를 설정하면 우선 적용된다.

3. 애플리케이션 실행
   ```bash
   ./gradlew bootRun
   ```
   실행 후 `http://localhost:8080` 접속
